# 直す順番

先に損失の中だけを直し、次にデータの切り方を決め、その上で学習ループを汎用化する。行動選択の速さは、ループの呼び出し口が決まってから差し替える。

## 気になっている点

- `main` と `train` が今の Point1D 実験に依存しすぎている。他の環境の実験にも対応できるようにしたい。
- `collect_episode` はエピソードが終わる環境前提。ステップ数で区切ってそのたびに学習し、環境が継続するものにも対応したい。
- KL バランシングは入れた。`kl_balance` は消し、`dyn_scale`（既定 1.0）と `rep_scale`（既定 0.1）で、勾配を分けた2本の KL を足す。
- データ収集から学習をループにする。2周目以降は学習したモデルでデータ収集を行う。今は候補で集めた軌道をバッファに足すが、そのデータで世界モデルを更新し直していない。
- この環境の行動選択が遅すぎる。行動系列のサンプリングに時間がかかりすぎるので、もう少しいい方法を使う。

## 1. KL バランシング（済）

`observe` が `kl_dyn`（事後を止めた KL）と `kl_rep`（事前を止めた KL）を返す。`world_model_loss` はそれぞれを `free_nats` で下から切り、`kl_scale * (dyn_scale * dyn + rep_scale * rep)` を損失に入れる。係数の既定は DreamerV3 の `loss_scales` と同じで、`dyn_scale = 1.0`、`rep_scale = 0.1`。

## 2. 収集の単位をエピソードからチャンクへ

`collect_episode`、`ReplayBuffer.add_episode`、`sample_paths` は、終わったエピソードが1本ある前提である。継続する環境では `done` が来ないので、この関数のままでは学習まで到達しない。

固定ステップ数で区切り、そのチャンクをバッファに入れ、そこで世界モデルを更新する収集にする。`reset` は環境が実際に始まった時刻だけ真にする。今の Point1D は、`done` でチャンクが早めに終わる特別な場合として残す。学習が受け取るバッチの形 `(obs, act, rew, reset)` はそのままにする。

この形が、次のループと、他の環境でも同じドライバを使うことの両方の入り口になる。

## 3. 収集と学習のループ、および train の汎用化

この二つは同じ変更である。今の `train` は、Point1D の次元、ホライズン、`3^4 = 81`、ランダム収集を1回、世界モデル、候補の評価、方策、という一回きりの手順が関数本体に書いてある。

`train` は環境と設定を受け取る繰り返しにする。

1. 1周目はランダムにチャンクを集めて世界モデルを更新する。
2. 2周目以降は、その時点のモデルで `select_action` して集め、世界モデルを更新する。方策モードなら方策も更新する。

Point1D の数値や離散・連続の切り替えは、実験側のスクリプトに移す。収集の戻り値と更新関数の呼び方は、どの環境でも同じにする。

## 4. 行動選択を速くする

候補モードは、毎ステップで長さ `horizon` の列を作り、全列の期待自由エネルギーを計算し、最小の先頭1手だけを実行する。`select_action` はこの評価を JIT していない。ループで候補モードのままデータを集めると、このコストが周回のたびにかかる。

ループ側は `select_action` を呼ぶだけにしておき、列の出どころは `CandidatePlanner` の中で差し替える。全列挙や一様サンプルを、少ないサンプルから有望な列の周辺を引き直す方法に変える。評価関数 `evaluate_action_sequences` は共通のまま使う。

候補モードでループを回しながらこの方法を試すなら、その前に評価部分だけ JIT して、今の全列挙でも1周が終わる状態にしておく。そうすると方法の差を測れる。方策モードで集めるなら、この速さはループの動作確認を止めない。
